# 10. AI 활용 명세 (결과보고서용)

> 버전: v1.0 · 기준일: 2026-08-13 · 상태: **P4 설계 기준** · 용도: 결과보고서 PPT

## 0. 전제 — 이 제품에서 AI가 하는 일과 하지 않는 일

발표에서 가장 먼저 정리해야 할 경계다.

| 기능 | 담당 | AI인가 |
| --- | --- | --- |
| 주문을 열차·화차·슬롯에 배정 | OR-Tools CP-SAT (제약조건 최적화) | 아니오 |
| 하드 제약 판정(시간·규격·중량·터미널) | 규칙 엔진 | 아니오 |
| 대안 가능 여부 계산 | CP-SAT 재실행 | 아니오 |
| **비정형 운송 의뢰서 → 주문 데이터 구조화** | **생성형 AI** | 예 |
| **계산 결과·미배정 사유를 운영자 문장으로 설명** | **생성형 AI** | 예 |

배정 결정을 생성형 AI가 하지 않는 이유는 재현성과 안전성이다. 같은 입력에 같은 결과가 나와야 하고, 규격·중량·안전 제약을 모델이 임의로 완화하면 안 된다. AI는 **사람이 쓴 글을 계산 가능한 데이터로 바꾸는 입구**와 **계산 결과를 사람이 읽는 문장으로 바꾸는 출구**를 맡는다.

## 1. 사용 모델 또는 AI 제품

| 항목 | 값 |
| --- | --- |
| 제품 | OpenAI API |
| 모델 | GPT 계열 · 정확한 모델 ID는 **[확인 필요]** (당일 계정에서 사용 가능한 최신 모델로 고정) |
| 사용 기능 | Structured Outputs (JSON Schema 강제 출력) |
| 호출 방식 | 백엔드(FastAPI)에서 서버 사이드 호출. 키는 `.env`의 `OPENAI_API_KEY` |
| 호출 지점 | 2곳 (인테이크 1회, 설명 1회) |
| 최적화 엔진 | OR-Tools CP-SAT — AI 모델이 아님 |

## 2. 모델 선택 이유

1. **JSON Schema 강제 출력을 지원한다.** 이 제품의 입력은 자유 텍스트가 아니라 `ScenarioInputSnapshot`이라는 typed 스키마다. 모델이 스키마 밖 필드를 만들거나 형식을 깨면 파이프라인 전체가 멈춘다. Structured Outputs로 출력 형식을 강제하면 파싱 실패와 필드 환각을 구조적으로 차단할 수 있다.
2. **한국어 비정형 문서 처리가 가능하다.** 실제 운송 의뢰는 정형 폼이 아니라 메일·메신저 문장으로 온다. 한국어 문장에서 시각·규격·중량·터미널을 추출해야 한다.
3. **응답 지연이 데모에 적합하다.** 시연 중 실시간 호출이므로 수 초 내 응답이 필요하다.
4. **팀 보유 크레딧이 OpenAI 계정에 있다.** (실무 제약)

Anthropic Claude SDK도 설치해 두었으나 이번 구현에서는 사용하지 않는다. 두 제품 모두 위 1~3을 만족하므로, 선택 기준은 팀의 가용 크레딧이었다.

## 3. AI 역할

### 3.1 역할 A — 인테이크 (비정형 의뢰서 구조화)

운영자가 받은 운송 의뢰 메일·메시지를 주문 데이터로 바꾼다.

- 문장에서 출발·도착지, 준비 시각, 납기, 규격, 중량, 취급 조건을 추출한다.
- **모르는 값은 추정하지 않고 `null`로 두고 누락 필드로 표시한다.** 이 값이 그대로 `input_state = REVIEW_REQUIRED`(화면 표시: `확인 필요`)로 이어진다.
- 각 필드가 원문의 어느 문구에서 나왔는지 근거를 함께 반환한다.

### 3.2 역할 B — 설명 생성

검증을 통과한 계산 결과를 운영자가 읽는 문장으로 바꾼다.

- 입력은 검증된 `explanation_bundle`(주문 상태·사유 코드·대안 결과)뿐이다.
- 원본 결과에 없는 수치, 확률, 원인을 새로 만들지 않는다.
- 생성 후 주문 ID·상태·사유 코드가 원본과 일치하는지 대조하고, 불일치하면 정형 템플릿 문장으로 대체한다.

### 3.3 AI가 하지 않는 것 (발표 시 명시)

- 어떤 주문을 어느 슬롯에 배정할지 결정하지 않는다.
- 하드 제약(높이·중량·마감·터미널) 통과 여부를 판정하지 않는다.
- 누락된 중량·납기를 추정해 채우지 않는다.
- 비용·탄소·성공 확률 같은 계산되지 않은 수치를 만들지 않는다.

## 4. 프롬프트 설계

### 4.1 설계 원칙

| 원칙 | 이유 |
| --- | --- |
| 추정 금지, 모르면 `null` | 임의 보정된 값으로 편성하면 운영 판단을 오도한다. 누락은 `확인 필요`로 사람에게 넘긴다 |
| 폐쇄형 vocabulary만 선택 | 터미널 ID·호환 태그·우선순위는 제공된 목록에서만 고른다. 새 ID를 만들면 참조 무결성이 깨진다 |
| 상대 시각은 `as_of` 기준 절대시각 변환 | "내일 오전"을 ISO 8601 + 시간대로 확정해야 제약 계산이 가능하다 |
| 필드마다 근거 문구 필수 | 운영자가 추출 결과를 원문과 대조할 수 있어야 한다 |
| JSON Schema 강제 출력 | 형식 오류와 스키마 밖 필드를 차단한다 |
| 출력 후 Pydantic 재검증 | 모델 출력을 신뢰하지 않고 서버에서 한 번 더 검사한다. 실패 시 해당 주문은 `REVIEW_REQUIRED` |

### 4.2 인테이크 프롬프트 구조

```text
[System]
너는 철도 피기백 운송 주문 접수 담당이다. 주어진 의뢰 문장에서 주문 정보를 추출한다.
규칙:
1. 문장에 명시되지 않은 값은 추정하지 말고 null로 둔다.
2. terminal_id, compatibility_tags, priority_class는 제공된 목록의 값만 사용한다.
3. 상대 시각은 as_of 기준 절대시각(ISO 8601 +09:00)으로 변환한다.
4. 길이·폭·높이는 mm 정수, 중량은 kg 정수로 변환한다.
5. 각 필드에 대해 근거가 된 원문 문구를 field_evidence에 남긴다.
6. 판단이 애매한 해석은 assumptions_flagged에 기록한다.

[Input]
as_of: 2026-08-16T18:00:00+09:00
terminals: [TRM-A(인천 합류), TRM-B(부산 도착), TRM-C(대전 대체)]
compatibility_tags: [TRAILER_STANDARD, TRAILER_TALL]
priority_class: [P1, P2, P3]
document: <의뢰서 원문>

[Output]
response_format = json_schema (OrderDraft 스키마 강제)
```

### 4.3 설명 프롬프트 구조

```text
[System]
너는 편성 결과를 운영자에게 설명한다.
규칙:
1. 입력 JSON에 있는 사실만 사용한다. 새 수치·확률·원인을 만들지 않는다.
2. 주문 ID와 사유 코드는 입력 값 그대로 인용한다.
3. 2~3문장으로 쓴다. 무엇이 안 됐는지, 왜인지, 무엇을 바꾸면 되는지 순서로 쓴다.
4. 실제 운행 가능성, 비용·탄소 절감을 주장하지 않는다.

[Input]
검증 통과한 explanation_bundle (주문 상태 4축, primary_reason_code, 대안 결과)
```

## 5. 입력값

| 역할 | 입력 | 형식 |
| --- | --- | --- |
| A 인테이크 | 운송 의뢰서 원문 | 자유 텍스트 (메일·메신저 문장) |
| A 인테이크 | `as_of` 기준 시각 | ISO 8601 + 09:00 |
| A 인테이크 | 터미널·태그·우선순위 목록 | 폐쇄형 vocabulary |
| B 설명 | `explanation_bundle` | 검증 통과한 구조화 JSON. 원문 텍스트나 미검증 값은 넣지 않는다 |

## 6. 출력값

| 역할 | 출력 | 이후 처리 |
| --- | --- | --- |
| A 인테이크 | `order_draft` (주문 필드, 미상은 null) | Pydantic 검증 → 시나리오 입력 |
| A 인테이크 | `missing_fields`, `review_reasons` | `input_state = REVIEW_REQUIRED` 판정 근거 |
| A 인테이크 | `field_evidence` (필드별 근거 문구) | 화면에서 원문 대조 표시 |
| A 인테이크 | `assumptions_flagged` (해석 가정) | 운영자 확인 대상 |
| B 설명 | 운영자용 설명 문장 | 원본 대조 후 표시. 불일치 시 템플릿 문장 |

## 7. 예시

### 7.1 입력 — 데모용 의뢰서 원문 [가정]

```text
안녕하세요, OO물류 김대리입니다.
내일(8/17) 인천에서 부산으로 트레일러 한 대 보내려고 합니다.
오전 9시부터 반출 가능하고, 늦어도 저녁 6시까지는 도착해야 합니다.
차량은 13.6m 표준 트레일러이고 높이는 3.9m입니다.
확인 부탁드립니다.
```

### 7.2 출력 — 구조화 결과

```json
{
  "order_draft": {
    "origin_terminal_ids": ["TRM-A"],
    "destination_terminal_ids": ["TRM-B"],
    "ready_at": "2026-08-17T09:00:00+09:00",
    "due_at": "2026-08-17T18:00:00+09:00",
    "gross_weight_kg": null,
    "dimensions_mm": {"length": 13600, "width": null, "height": 3900},
    "compatibility_tags": ["TRAILER_STANDARD"],
    "priority_class": null
  },
  "field_evidence": [
    {"field": "ready_at", "source_text": "오전 9시부터 반출 가능"},
    {"field": "due_at", "source_text": "늦어도 저녁 6시까지는 도착"},
    {"field": "dimensions_mm.height", "source_text": "높이는 3.9m"}
  ],
  "missing_fields": ["gross_weight_kg", "dimensions_mm.width"],
  "review_reasons": [
    {"field": "gross_weight_kg", "reason_code": "MISSING_REQUIRED_FIELD"}
  ],
  "assumptions_flagged": [
    {"field": "destination_terminal_ids", "note": "'부산'을 TRM-B로 해석함"},
    {"field": "ready_at", "note": "'내일'을 as_of 기준 2026-08-17로 해석함"}
  ]
}
```

### 7.3 이 출력이 화면에서 되는 일

총중량이 없으므로 이 주문은 `input_state = REVIEW_REQUIRED`가 되어 **확인 필요**로 분리되고, 편성 계산 대상에서 제외된다. 정본 fixture의 `ORD-006`과 같은 장면이다.

> 발표 문구: "AI가 모르는 값을 채워 넣지 않습니다. 총중량이 없다는 사실을 찾아내 계산 대상에서 분리하고, 운영자에게 확인을 요청합니다."

### 7.4 역할 B 출력 예시

입력(검증된 결과):

```json
{"order_id": "ORD-004", "eligibility_state": "ELIGIBLE", "assignment_state": "UNASSIGNED",
 "primary_reason_code": "CAPACITY_CONFLICT", "alternative_state": "AVAILABLE",
 "alternative": {"type": "ADD_ORDER_APPROVED_SERVICE", "service_id": "SVC-NEXT-01"}}
```

출력 문장:

```text
ORD-004는 시간·규격·중량 조건을 모두 만족하지만, 이번 운행의 슬롯 3개가 우선순위가 높은
주문에 배정되어 선택되지 않았습니다(CAPACITY_CONFLICT). 승인된 다음 운행 SVC-NEXT-01을
추가하면 배정 가능한 대안이 있습니다.
```

이 문장의 모든 사실(주문 ID, 사유 코드, 대안 운행 ID)은 입력 JSON에 있는 값이다. 문장 생성 후 서버가 이를 대조한다.

## 8. PPT 슬라이드 구성 제안

| 슬라이드 | 내용 |
| --- | --- |
| AI 경계 | §0 표 — 무엇을 CP-SAT가, 무엇을 AI가 하는가 |
| 모델·선택 이유 | §1 표 + §2의 1·2번 (Structured Outputs, 한국어 비정형) |
| AI 역할 | §3 인테이크·설명 2지점 + "하지 않는 것" |
| 프롬프트 설계 | §4.1 원칙 표 (추정 금지·폐쇄형 vocabulary·근거 필수) |
| 예시 | §7.1 원문 → §7.2 JSON → §7.3 확인 필요 화면 (한 장에 흐름) |

## 9. 용어

- **피기백**: 트레일러·화물차량을 화차에 실어 철도로 운송하는 방식.
- **화차**: 열차에 연결되는 화물 운반 차량. 이 제품에서는 슬롯 여러 개를 가진다.
- **슬롯**: 트레일러 한 대가 올라가는 자리. 배정의 최소 단위.
- **편성**: 어떤 주문을 어느 열차·화차·슬롯에 실을지 정하는 일.
- **컷오프(반입 마감)**: 해당 운행에 실으려면 그 시각까지 터미널에 물건이 들어와야 하는 기한.
- **CP-SAT**: 제약조건을 만족하는 배정을 찾는 최적화 엔진. 생성형 AI가 아니다.
