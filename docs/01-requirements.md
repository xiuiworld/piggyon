# 01. MVP 요구사항 정의서

> 버전: v1.0 · 기준일: 2026-08-10 · 상태: **구현 기준 최종본**

## 1. 제품 한 문장

후보 터미널과 터미널 기준 `ready_at`·`due_at`이 정리된 운송 주문을 제한된 운행·화차·슬롯에 배정하고, 미배정 사유와 승인된 조건부 대안을 보여 주는 **시나리오 기반 운영 의사결정 지원 MVP**다.

## 2. 해결할 사용자 판단

운영자는 한 화면에서 다음을 판단해야 한다.

1. 어떤 주문이 입력 부족으로 계산 대상이 아닌가?
2. 각 주문은 현재 기본 운행·터미널·슬롯 조건에서 적합한가?
3. 적합한 주문 중 무엇을 제한된 슬롯에 배정할 것인가?
4. 미배정 주문은 물리적으로 불가한지, 용량 경합인지, 승인된 변경으로 재검토 가능한지?
5. 기본안과 대안 중 무엇을 채택·보류할 것인가?

## 3. 사용자와 책임

| 역할 | 시스템에서 하는 일 | 시스템 밖의 책임 |
| --- | --- | --- |
| 편성 운영자 | 시나리오 검토, 안 비교, 채택·보류 기록 | 최종 운영 판단 |
| 운영 기획자 | 데모 정책·대안 범위 검토 | 우선순위 정책 승인 |
| 협의 담당자 | 대안의 협의 필요 사항 확인 | 실제 변경 합의 |

MVP에서는 한 사람이 모든 역할을 수행할 수 있지만, 결정 기록에는 역할과 사유를 남긴다.

## 4. Must MVP 범위

- 버전된 시나리오 입력과 필수값·시간·단위 검증
- 시간·경로·터미널·규격·중량·자원 가용성의 하드 제약 판정
- 주문-운행-화차-슬롯 기본 배정안 1개 생성
- 주문별 상태, 사유 코드, 증거와 다음 조치 표시
- 승인된 다음 운행 또는 승인된 대체 터미널을 적용한 대안 생성
- 기본안과 대안을 별도 시나리오로 저장·비교
- 결과를 독립 검증기로 재검산
- 입력 → 결과 → 대안 → 결정의 단일 데모 흐름

## 5. 명시적 제외 범위

- 실제 열차 운행 지시, 관제 제어, 자동 확정
- 원시 트럭 운송장에서 피기백 전환 후보를 새로 발굴하는 기능
- 실제 운영 성과, 비용 절감, 탄소 절감, 배정 확률의 주장
- 실제 예약·결제·정산·고객 관리 연동
- 실제 도로 이동시간 최적화. 지도는 경로 맥락을 보여 주는 시각화 전용이다.

## 6. 핵심 기능 요구사항

### FR-01 시나리오와 입력 검증

- 시스템은 주문·운행·화차·슬롯·터미널·정책의 불변 입력 스냅샷을 만든다.
- 필수값 누락, 단위 오류, 존재하지 않는 참조, 시간 모순은 주문 또는 자원 단위로 보고한다.
- 필수값이 없는 주문은 임의 보정하지 않고 `REVIEW_REQUIRED`로 격리한다.

### FR-02 적합성 및 기본 편성

- 적합성 게이트는 모든 하드 제약을 통과한 주문-운행-슬롯 쌍만 만든다.
- 편성 엔진은 각 주문을 최대 한 슬롯, 각 슬롯을 최대 한 주문에 배정한다.
- 후보는 있지만 선택안에서 빠진 주문을 `INELIGIBLE`로 표시하지 않는다.

### FR-03 사유와 설명

- 모든 주문 결과는 핵심 사유 코드, 증거, 다음 조치를 가진다.
- 설명 문구는 구조화된 결과에서만 만들며, 계산되지 않은 수치나 원인을 추가하지 않는다.

### FR-04 조건부 대안

- 대안은 정책에 등록된 변경만 적용한다.
- 변경 후보는 별도 `change_set`을 가진 파생 시나리오로 재계산한다.
- 규격·중량·터널 여유·필수 안전 제약은 완화할 수 없다.
- 성공한 대안은 영향 주문과 `assignment_deltas`의 전후 배정을 함께 반환한다. 허용 범위를 모두 탐색해도 대안이 없으면 `NO_FEASIBLE_ALTERNATIVE`로 종료한다.

### FR-05 운영자 결정

- 운영자는 기본안 또는 대안을 `ACCEPTED`, `HELD`, `REJECTED` 중 하나로 기록한다.
- 결정은 시나리오, 실행 ID, 정책 버전, 결정 사유와 함께 저장한다.

## 7. 비기능 요구사항

- **안전한 실패:** 검증기 실패 또는 불명확한 실행 상태는 채택 불가로 처리한다.
- **재현성:** 입력·정책·솔버 설정이 같고 모든 목적 단계가 `OPTIMAL`이면 정규화된 결과가 같아야 하며, 입력·정책·결과 SHA-256과 솔버 설정을 실행 결과에 보존한다.
- **추적성:** 결과에는 시나리오·정책·가정·실행 ID와 대안의 전후 배정 차이를 남긴다.
- **개인정보 최소화:** 화주명, 연락처, 차량번호, 정확한 주소, 운임은 입력하지 않는다.

## 8. 데모 승인 기준

1. 하드 제약 위반과 중복 슬롯 배정이 0건이다.
2. 정상 배정, 입력 누락, 용량 경합, 시간 대안, 완화 불가 사례를 모두 보여 준다.
3. 모든 주문에 상태·사유·다음 조치가 있다.
4. 모든 운영 수치가 `DEMO_ASSUMPTION` 또는 확인 가능한 출처로 구분된다.
5. `ACCEPTED` 결정은 `solver_status = OPTIMAL`과 `validator_status = PASS`를 모두 만족한 실행에서만 가능하다. `FEASIBLE`은 보류·반려만 가능하다.

## 9. 팀 결정이 필요한 항목

- 데모 정책의 목적함수 순서
- 기본 운행 집합과 대안 전용 다음 운행
- 대안으로 허용할 다음 운행·대체 터미널 목록
- 우선순위 등급과 동률 처리 규칙

## 10. 동결된 구현 결정

| ID | 최종 결정 | 이유 |
| --- | --- | --- |
| DEC-01 | 편성 엔진은 OR-Tools CP-SAT만 사용한다. | 하드 제약·사전순 목적함수·재현성 검증을 한 모델로 관리한다. |
| DEC-02 | 정본 입력은 `fixtures/canonical-v1/scenario.json`이다. | 프론트·API·테스트가 같은 9건 주문을 사용한다. |
| DEC-03 | 기본 운행 집합은 `SVC-AM-01` 하나다. | 3개 슬롯과 4개 적합 주문의 용량 경합을 확실히 보여 준다. |
| DEC-04 | 허용 대안은 승인된 다음 운행 추가와 승인된 도착 터미널 변경뿐이다. | 대안의 범위를 유한하게 만들고 변경 영향을 설명한다. |
| DEC-05 | 생성형 AI는 필수가 아니다. MVP 필수 설명은 구조화된 템플릿이며, LLM을 연결해도 검증된 `explanation_bundle` 밖의 사실을 만들 수 없다. | 구현 실패가 설명 계층 때문에 전체 데모를 막지 않게 한다. |
| DEC-06 | 모든 수치와 좌표는 `DEMO_ASSUMPTION`이다. | 실제 운영 가능성·효과·확률과 분리한다. |

## 11. Definition of Ready

개발 시작 전 아래가 모두 충족되어야 한다.

- `scenario.json`과 `expected-results.json`이 JSON 파싱된다.
- `SVC-AM-01`, `SVC-NEXT-01`, `SVC-AC-01`과 주문 `ORD-001`~`ORD-009`이 존재한다.
- API는 `docs/openapi.yaml`을 계약 정본으로 사용한다.
- 화면은 08 문서의 6개 화면과 상태 문구를 사용한다.
